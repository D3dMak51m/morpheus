# SIMULATION — изолированный полигон MORPHEUS

Отдельная среда для тестирования **агентов / душ / ИИ-личностей, миссий, RAG,
системных промптов, комментариев, реакций, массовой генерации и сценариев
поведения** — с Telegram-подобным UX и полным ручным редактированием любого
состояния. Полностью изолирована от боевой части системы.

Вкладка в DAEDALUS: **ПОЛИГОН → Симуляция** (`#/simulation`, тред — `#/simulation/<post_id>`).

---

## 1. Контракт изоляции (чем гарантируется)

| Уровень | Как изолировано |
|---|---|
| Схема БД | Все таблицы в namespace `sim_*` и на **отдельном** `SimBase` (`app/models_simulation.py`). Ни одного FK в боевые таблицы. |
| API | Единый префикс `/api/v1/simulation/*`, отдельные RBAC-атомы `simulation:view` / `simulation:manage`. |
| Очереди | Собственная очередь **`queue:sim_gen`** + ответы `reply:simgen:<id>`. Никогда не используется `queue:execution_tasks` — значит, ни одно действие полигона физически не может попасть в MYRMIDON и в реальный Telegram. |
| Память/метрики | ORPHEUS обслуживает полигон отдельным обработчиком (`orpheus/app/simulation.py`): **не пишет** MUNINN, `morpheus:recent_outputs:*` и `metrics:*`. |
| Импорт | Боевые таблицы только **читаются** (SELECT) и копируются в `sim_*`. Ни одна боевая строка не изменяется. |
| Лимиты | Внутри полигона **не действуют** production-ограничения: нет rate-лимитов (≤1/канал/час, ≤4/агент/час), кулдаунов и окна активных часов. |

Проверено на живом стенде: после 6 сгенерированных реплик и запуска миссии
`metrics:comments_sent`, `agent_activity_logs`, `morpheus:recent_outputs:*`,
`queue:execution_tasks`, `missions`, `knowledge_facts` остались неизменными.
В тестах изоляция закреплена структурно: тестовая БД содержит **только** `sim_*`
таблицы, поэтому любая запись в боевую таблицу упала бы с «no such table».

## 2. Сущности (`daedalus/app/models_simulation.py`)

| Таблица | Сущность | Роль |
|---|---|---|
| `sim_worlds` | **Симуляция** | Изолированный полигон; их может быть несколько, переключатель в шапке. |
| `sim_channels` | **Канал** | Источник постов (@username, title, гео, темы, подписчики, цвет). |
| `sim_posts` | **Пост** | Объект обсуждения. Принадлежит **каналу**, не аккаунту. Медиа (изображение/видео/аудио/документ/ссылка), реакции, просмотры, время — всё редактируется. |
| `sim_post_revisions` | История поста | Снимок состояния перед каждой правкой + откат. |
| `sim_comments` | **Комментарий** | Дерево (self-FK `parent_id`), автор = аккаунт / агент / внешний голос, реакции, статус, время, meta с трассировкой генерации. |
| `sim_accounts` | **Аккаунт** | **Ручной** исполнитель (оператор). ИИ им не управляет. Инициалы, имя, цвет, статус, описание. |
| `sim_personas` | **Агент / душа** | Тестируемая ИИ-личность: био, интересы, стиль (4 слайдера + речевые особенности), **системный промпт**, паттерны. |
| `sim_missions` + `sim_mission_agents` | **Миссия** | Сценарий, объединяющий агентов: цель, `stance`, мировоззрение, тактика, режим, scope. **Плюс явная позиция как в бою** — `our_side` / `opponent` / `key_points` / `red_lines`: ORPHEUS собирает из них тот же блок «[Твоя сторона в этом споре]», что и `persona.assemble_mission_prompt`, и импорт боевой миссии её переносит. Без этого полигон репетировал заведомо более слабую миссию. Только внутри симуляции. |
| `sim_knowledge` | **Знания** | Собственная RAG-база: `fact / news / rule / prompt / channel_profile / history`. |
| `sim_mission_dossier` | **Досье миссии** | Общая память ростера, как в бою: `fact` / `opponent` / `counter` / `said`. `said` привязан к посту — повтор в одной ветке выдаёт рой, повтор в другой ветке нормален. Пишется после каждой удачной генерации, подаётся в промпт тремя блоками. |
| `sim_mission_outcomes` | **Исход** | Тон до/после и вовлечение — те же метрики, что в бою. В полигоне «после» не требует ожидания: ветка наша. |
| `sim_landscape_sources` | **Ландшафт** | Определения внешних источников и результат их запусков. |
| `sim_jobs` | Задание | Прогон массовой генерации с прогрессом. |
| `sim_events` | **Активность** | Журнал: `создано / сгенерировано / отправлено / запланировано / ошибка / завершено`. |

## 3. API (`daedalus/app/router_simulation.py`)

```
GET/POST/PUT/DELETE  /worlds[/{id}]        + /worlds/{id}/seed, /worlds/{id}/reset
GET                  /state                 — один бутстрап-вызов для консоли
GET/POST/PUT/DELETE  /channels[/{id}]
GET/POST/PUT/DELETE  /posts[/{id}]          + /posts/{id}/revisions[/{rid}/restore], /posts/{id}/reactions
GET                  /posts/{id}            — пост + всё дерево комментариев (режим треда)
POST/PUT/DELETE      /comments[/{id}]       + /comments/{id}/{reactions,publish}
GET/POST/PUT/DELETE  /accounts[/{id}], /personas[/{id}]
GET                  /personas/{id}/export  — личность в формате боевой души
GET/POST/PUT/DELETE  /missions[/{id}]       + /missions/{id}/agents, /missions/{id}/run
GET/POST/PUT/DELETE  /knowledge[/{id}]      + /knowledge/import
GET/POST/PUT/DELETE  /landscape[/{id}]      + /landscape/{id}/run, /landscape/scrape
POST                 /generate              — один комментарий/ответ (синхронно)
POST                 /generate/post         — пост или статья для канала
POST                 /generate/batch        — массовая генерация (фоновое задание)
GET/POST             /jobs, /jobs/{id}/cancel
GET/DELETE           /events                — лента активностей с фильтрами
GET                  /inspect/{entity}/{id} — сырое состояние любой сущности
GET                  /health
```

## 4. Как работает генерация

```
DAEDALUS  /generate | /generate/post | /generate/batch
   ├─ retrieve_knowledge()  — лексический RAG по sim_knowledge (детерминированно,
   │                          без GPU; операторy видно, какие факты попали в промпт)
   ├─ system_rules()        — знания типов rule/prompt подставляются всегда
   └─ LPUSH queue:sim_gen ──▶ ORPHEUS handle_simulation_generation()
                                 ├─ build_sim_prompt()  (persona → rules → RAG →
                                 │   channel → post → thread → тактика → задача)
                                 │   либо prompt_override с плейсхолдерами
                                 ├─ generate_text() (Ollama, тот же движок, что в бою)
                                 ├─ guardrails: отклонённый черновик ВОЗВРАЩАЕТСЯ
                                 │   с пометкой guardrail=failed — полигон должен
                                 │   показывать, что бой бы забраковал
                                 └─ LPUSH reply:simgen:<id>  {text, prompt, …}
```

Плейсхолдеры `prompt_override`: `{persona} {persona_name} {system_prompt} {channel}
{post} {media} {thread} {knowledge} {rules} {goal} {stance} {worldview} {tactic}
{incoming} {incoming_author} {tone}`.

Если ORPHEUS/Ollama недоступен — артефакт сохраняется со статусом **ошибка** и
причиной (никаких подставных текстов).

## 5. Ландшафт и импорт

**Скрапинг** (только чтение открытых источников):
* `rss` — RSS/Atom (парсер на stdlib, без новых зависимостей);
* `web` — статья/страница (извлечение читаемого текста);
* `tg_preview` — публичное веб-превью Telegram `t.me/s/<channel>`: **без аккаунта,
  без сессии, без MTProto** — только то, что видит анонимный браузер.

Результат складывается либо постами в канал полигона (с медиа и ссылками), либо
записями в RAG-базу.

**Импорт из боевой системы** (`POST /knowledge/import`, `what=`):
`knowledge` (факты RAG) · `channel_profiles` (+ создаёт каналы) · `landscape`
(источники) · `souls` (души → агенты полигона) · `missions` (боевые миссии →
сценарии полигона) · `history` (реальные реплики роя из `agent_activity_logs`).

**Импорт постов ВМЕСТЕ с комментариями реальных людей**
— в UI: правая колонка → **«Импорт поста из Telegram»**
(`POST /simulation/import/telegram`):

```json
{"source": "https://t.me/tashkent_news333/35"}
```

`source` — то, что у оператора реально есть: **ссылка на пост**. Ссылка с номером
переносит именно этот пост вместе с веткой; ссылка на канал (`@channel`) — последние
`post_limit` постов. Чья сессия читает, выбирается автоматически (любой агент с живым
Telegram-аккаунтом) — это деталь реализации, а не решение оператора.

Публичное превью `t.me/s/<channel>` комментарии не показывает — они лежат в
связанной группе обсуждения и доступны только по MTProto. Поэтому чтение
делегируется сессии MYRMIDON (`GET /api/v1/telegram/{agent_id}/export` на порту
8003), а DAEDALUS только раскладывает результат по `sim_*`. Операция **строго на
чтение**: ничего не публикуется, никуда не вступает, реакции не ставятся.

* посты → `sim_posts` (`source='imported'`, ключ `external_ref`);
* комментарии → `sim_comments` (`author_kind='external'`, `origin='imported'`),
  дерево ответов сохраняется, **исходные даты не подменяются** — иначе тред
  читается как залп, а не как разговор. Тред обходится **хронологически**: Telegram
  отдаёт ответы новейшими вперёд, поэтому при наивной вставке ответ попадает раньше
  того, на что он отвечает, и вся вложенность разваливается на плоский список;
* `meta.is_our_bot` отделяет прошлые реплики самого роя от чужих голосов;
* повторный запуск безопасен: посты сверяются по `external_ref`, комментарии по
  telegram-id.

Зачем: тред, населённый только оператором и своими же агентами, не проверяет ту
половину конвейера, которая читает **настоящую** толпу — настроение обсуждения,
выбор тактики под пост, анти-эхо, адресность ответа.

## 6. UI (`daedalus/frontend/src/components/simulation/`)

```
SimulationScreen.tsx     шапка (полигон/движок/демо-среда/очистка) + 3 колонки
├── ActivityFeed.tsx     ЛЕВО   — лента активностей, фильтры по событиям и статусам
├── ChannelFeed.tsx      ЦЕНТР  — посты канала (медиа, реакции, «Открыть комментарии»)
├── ThreadView.tsx       ЦЕНТР  — режим одного поста: дерево, ответы, реакции,
│                                 публикация, выбор аккаунта/агента, массовая генерация
├── RightPanel.tsx       ПРАВО  — каналы (поиск/создание/правка) + действия +
│                                 быстрый комментарий + исполнители + инспектор
├── EntityModals.tsx     канал / пост (+история, +генерация текста) / аккаунт / комментарий
├── AgentModals.tsx      агент (личность, стиль, системный промпт, экспорт) / миссия
└── ToolModals.tsx       массовая генерация / знания + импорт / ландшафт
```

Открытие комментариев переключает центральную колонку в режим одного поста и
меняет хеш на `#/simulation/<post_id>` (обновление страницы и «назад» работают).

**Полигон → бой:** отлаженную личность можно подставить в настоящую душу —
в разделе «Души» кнопка **«Из симуляции»** открывает список агентов полигона и
заполняет форму (в боевую БД ничего не пишется до нажатия «Сохранить»).

## 7. Тесты

```bash
docker compose exec daedalus python -m pytest tests -q   # 45 тестов
docker compose exec orpheus  python -m pytest tests -q   # 15 тестов
```

Покрыто: изоляция namespace/FK, миры и сброс, CRUD каналов/постов/комментариев,
история правок и откат, дерево комментариев и удаление ветви, смена автора,
реакции, миссии (запуск только внутри полигона), знания и выборка RAG, парсинг
RSS/tg-превью и обработка сетевых ошибок, генерация (успех, черновик, ошибка,
ответ в ветке, пост/статья), массовая генерация агентами и аккаунтами вместе,
отсутствие production-лимитов, лента активностей и инспектор, а также — на стороне
ORPHEUS — сборка промпта, override, режим поста и **отсутствие записи в память,
метрики и очереди**.

## 8. Что осталось за рамками

* Импорт комментариев из реальных TG-каналов (публичное превью их не отдаёт).
* Планировщик (`scheduled`) — статус есть в модели и в фильтрах ленты, но
  отложенный запуск заданий по времени не реализован: задания стартуют сразу.
* Медиа хранятся ссылкой/описанием (файлы не загружаются на диск полигона);
  агент «читает» подпись к вложению, как медиа-контекст в бою.
