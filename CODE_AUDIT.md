# MORPHEUS — аудит качества кода и архитектурные правила

**Дата:** 14 августа 2026. **Объём:** 26 641 строка Python в 6 сервисах + 7 204 строки
TypeScript. **Инструменты:** `ruff`, `radon`, `vulture`, `pytest-cov` и собственный анализатор
графа импортов (`tools/check_architecture.py`, написан в ходе аудита). Все проверки запускались в
одноразовом контейнере — в систему ничего не устанавливалось.

---

## 1. Оценка одной страницей

Код **работает и читается**: осмысленные имена, содержательные комментарии, объясняющие *почему*
так сделано, документированные измерения в docstring-ах. Это выше среднего для проекта такого
возраста.

Но он написан **без единого архитектурного контракта**. Каждый сервис устроен по-своему, слои
перепутаны, а точка входа превращена в библиотеку. Отсюда 12 циклов импорта, 118 ленивых импортов
и — это уже не теория — реальная взаимоблокировка, которая вчера остановила исполнительный цикл в
бою.

Второе системное упущение — **отсутствие любой автоматической проверки**: нет CI, нет конфигурации
линтера, нет форматтера, нет pre-commit. Единственный барьер качества — ревью человеком, а он, как
показал вчерашний день, пропускает и вызов несуществующего метода, и самоблокировку.

| срез | оценка |
|---|---|
| Читаемость, комментарии, именование | **хорошо** |
| Архитектурная дисциплина (слои, зависимости) | **плохо** |
| Обработка ошибок | **плохо** (311 широких перехватов) |
| Конфигурация | **плохо** (150 переменных, ни одной точки сборки) |
| Тесты | **слабо** (29 % покрытия, 1 интеграционный на всю систему) |
| Автоматизация качества | **отсутствует** |
| Фронтенд | **удовлетворительно** (строгий TS, но нет линтера и тестов) |

## 3. Архитектурные ошибки

### 3.1 Точка входа работает библиотекой — корневая ошибка
`myrmidon/app/main.py` одновременно: запускает сервис, держит цикл обработки очереди и хранит
инфраструктуру (`connect_postgres`, `connect_redis`, `get_agent_credentials`). Поэтому **7 модулей
из 10 импортируют `main`**, а `main` импортирует их — получается **10 циклов**:

```
main -> device_api      -> drivers.tg_client -> main
main -> dialogue_engine -> drivers.tg_client -> main
main -> outcome_engine  -> drivers.tg_client -> main
```

Лечили это ленивыми импортами внутри функций — **54 штуки в одном myrmidon**. Цена оказалась не
косметической: чтение ветки внутри задачи вызывало `swarm_identities`, та открывала сессию того же
агента, чей лок держала задача, — и единственный потребитель очереди вставал намертво. Дефект
найден и закрыт вчера, но причина — эта схема зависимостей.

Итог по проекту: **12 циклов, 87 ленивых импортов**.

| сервис | циклов | ленивых импортов | импортируют `main` |
|---|---|---|---|
| myrmidon | 10 | 54 | 7 |
| daedalus | 1 | 30 | 0 |
| orpheus | 1 | 3 | 1 |
| huginn | 0 | 0 | 0 |

### 3.2 Два несовместимых способа работы с одной базой
DAEDALUS работает через ORM (модели, сессии, `Depends(get_db)`), MYRMIDON — **только сырым SQL**:
20 вызовов `text(...)`, **ноль импортов моделей**. Схема продублирована в SQL-строках, и
переименование колонки ломает второй сервис молча, без ошибки импорта и без падения тестов.
В самом DAEDALUS смешение тоже есть: 42 вызова `text(...)` рядом с ORM.

### 3.3 Общий код скопирован и разошёлся
`telemetry.py` существует в двух сервисах с **разным содержимым**: 64 строки в orpheus против 76 в
myrmidon, контрольные суммы не совпадают. Это не «намеренное дублирование ради независимости
сервисов» — это копия, которая уже разъехалась и продолжит расходиться.

### 3.4 Толстые контроллеры
`router_simulation.py` — **2155 строк**: HTTP-слой, валидация, бизнес-логика, запросы к БД и
работа с Redis в одном файле. Слоя сервисов нет ни в одном роутере; `router_missions.py` (1090) и
`router_knowledge.py` (976) устроены так же. Тестировать логику без HTTP невозможно — отсюда и
покрытие.

### 3.5 Схема базы меняется вручную
`alembic` объявлен в зависимостях, но каталога миграций **нет**; вместо него — блок ручных
`ALTER TABLE` в `database.py` (`_STAGE23_COLUMNS`). Значит: нет истории изменений схемы, нет
отката, нет воспроизводимости на чистой базе, а порядок применения зависит от того, что кто-то не
забыл дописать строку.

### 3.6 Ошибки глушатся
**311** конструкций `except Exception`, из них **26** молча проглатывают (`pass`/`continue`), и
**29** возбуждают новое исключение, теряя исходное (`raise ... ` без `from`). Наблюдаемость от
этого страдает предсказуемо: вчерашняя взаимоблокировка не дала ни одной строки ошибки — задача
просто перестала двигаться.

### 3.7 Конфигурация размазана
**262 вызова `os.getenv`, 150 уникальных переменных**, разбросанных по модулям (только в
`target_engine.py` — 24). Нет ни одного места, где видно, чем настраивается система; значения по
умолчанию дублируются в разных файлах и расходятся.

### 3.8 Глобальное изменяемое состояние
**28** объявлений `global` в 8 модулях: соединения, кэши, синглтоны. В сервисе, где работают
демон-потоки, это источник гонок, который не виден в тестах (они однопоточные).

### 3.9 Фронтенд
Плюсы: `strict: true`, `noUnusedLocals`, `noUnusedParameters` — сборка падает на мусоре, это
работает. Минусы: **нет ESLint**, **нет ни одного теста**, крупнейший компонент — 642 строки
(`MissionsScreen.tsx`), и в нём же смешаны загрузка данных, состояние формы и разметка.

## 4. Правила дальнейшей работы

Правила исполняемые: два артефакта добавлены этим аудитом и запускаются одной командой.

```bash
python3 tools/check_architecture.py     # циклы, ленивые импорты, main-как-библиотека
ruff check daedalus/app orpheus/app myrmidon/app huginn/app   # настроен в pyproject.toml
```

### Правило 0. Долг не растёт
`tools/check_architecture.py` хранит базу (`tools/architecture_baseline.json`) и **падает, если
стало хуже**. Разбирать унаследованное можно постепенно; добавлять новое — нельзя.

### Правило 1. Точка входа ничего не экспортирует
`app/main.py` только собирает и запускает. Инфраструктура (соединения, доступ к учётным данным,
клиенты) живёт в отдельных модулях: `app/db.py`, `app/redis_client.py`, `app/credentials.py`.
Ни один модуль не импортирует `app.main`. Это снимает разом циклы и ленивые импорты.

### Правило 2. Импорты только наверху файла
Исключение — тяжёлая загрузка (модель, драйвер) или временный разрыв цикла; обязательно с
пометкой `# lazy: причина`. Анализатор считает такие импорты отдельно и не ругается на них.

### Правило 3. Одна база — один способ доступа
Схему знает только DAEDALUS. MYRMIDON и другие сервисы получают данные через внутренние
HTTP-эндпоинты, а не через SQL-строки к чужим таблицам. Где сырой SQL оправдан
производительностью — он лежит в одном модуле-репозитории, а не по всему сервису.

### Правило 4. Роутер тонкий
Роутер: разбор запроса → вызов функции слоя логики → формирование ответа. Никаких запросов к БД,
Redis и правил в теле обработчика. Практический предел — **300 строк на файл роутера**; всё
сверх выносится в `app/services/<тема>.py`, который тестируется без HTTP.

### Правило 5. Функция помещается в голову
Порог сложности — **15** (`ruff` следит). Функция длиннее ~60 инструкций или с более чем 8
аргументами разбивается. Сборка промпта — не исключение: `assemble_mission_prompt` со сложностью
90 разбирается на блоки (персона, позиция, возражение, свежие данные, стиль), каждый из которых
можно проверить отдельно.

### Правило 6. Ошибку либо обрабатывают, либо она всплывает
`except Exception: pass` запрещён. Допустимо: перехват **конкретного** класса ошибок с записью в
лог и осмысленным продолжением. При повторном возбуждении — обязательно `raise ... from exc`.
Молчаливое проглатывание — это то, из-за чего вчерашний зависший цикл не оставил следа.

### Правило 7. Конфигурация в одном месте
Один модуль `app/config.py` на сервис: все переменные окружения, типы, значения по умолчанию и
документация — там. `os.getenv` в остальном коде не встречается.

### Правило 8. Состояние передают, а не прячут в модуле
Никаких `global`. Соединения и кэши живут в объекте, который создаётся при старте и передаётся
явно (или через `Depends`). Для демон-потоков это ещё и разница между воспроизводимой гонкой и
невоспроизводимой.

### Правило 9. Тест уровня, на котором произошла ошибка
Каждый найденный в бою дефект получает тест **того же уровня**: логика — юнит-тест, взаимодействие
сервисов — интеграционный. Цель на ближайший этап: **myrmidon с 8 % до 40 %**, и хотя бы один
интеграционный тест на публикацию (с подменённым Telegram).

### Правило 10. Схема меняется миграцией
Ввести alembic, перенести `_STAGE23_COLUMNS` в первую миграцию. Ручной `ALTER TABLE` в коде
запуска — запрещён.

### Правило 11. Проверки запускаются до ревью, а не после
Минимальный CI (или pre-commit): `ruff check`, `python3 tools/check_architecture.py`, три набора
тестов, `tsc --noEmit`. Пока CI нет — эти четыре команды выполняются вручную перед коммитом.

### Правило 12. Комментарий объясняет «почему»
Это в проекте уже хорошо, и это стоит сохранить: комментарии описывают измерение и причину
решения, а не пересказывают код. Правило простое — если из комментария нельзя понять, почему
нельзя сделать проще, комментарий не нужен.

## 6. Что в коде сделано хорошо (сохранить)

- **Комментарии объясняют причину и содержат измерения** — редкость, и именно они позволили
  провести этот аудит быстро.
- **Тесты в проекте пишутся на измеренные дефекты**, а не «для покрытия»; каждый несёт в docstring
  историю ошибки.
- **Изоляция полигона** от боевого контура выдержана честно: отдельная очередь, отдельные таблицы,
  отдельный обработчик — это правильно спроектированная граница.
- **Строгий TypeScript** во фронтенде: неиспользуемая переменная ломает сборку.
- **Документация верхнего уровня** (`CLAUDE.md`, `walkthrough.md`, `HANDOFF.md`) поддерживается в
  актуальном состоянии и реально экономит время входа в проект.

## Приложение. Как повторить аудит

```bash
# статический анализ (в одноразовом контейнере, ничего не ставится в систему)
docker run --rm -v "$PWD":/src -w /src python:3.11-slim bash -c \
  "pip install -q ruff radon vulture && \
   ruff check --statistics daedalus/app orpheus/app myrmidon/app huginn/app && \
   radon cc -s -n D daedalus/app orpheus/app myrmidon/app && \
   vulture daedalus/app orpheus/app myrmidon/app --min-confidence 80"

# архитектурные правила
python3 tools/check_architecture.py

# покрытие
for s in orpheus myrmidon daedalus; do
  docker compose exec $s pip install -q pytest-cov
  docker compose exec $s python -m pytest tests -q --cov=app --cov-report=term | tail -1
done
```
