Для проекта **MORPHEUS** микросервисная архитектура строится на разделении обязанностей: каждый сервис изолирован, имеет собственный контекст и общается с другими компонентами строго по протоколам HTTP REST API или через общую шину данных (Redis).

Ниже представлена подробная схема взаимодействия компонентов и сквозной макет циркуляции данных внутри системы.

## 2. Сквозной пайплайн прохождения данных

Чтобы понять, как компоненты работают «в динамике», проследим путь одного инфоповода:

### Шаг 1: Агрегация контента (HUGINN)

1. **HUGINN** непрерывно сканирует инфополе по целевым паттернам.
2. При нахождении публикации (например, видео-поста в Telegram-канале про инфраструктуру Ташкента) он скачивает медиа во временный локальный том `data_lake/raw_media/`.
3. Сервис проверяет временные метки (TTL) и присваивает новости слои: `State: Uzbekistan`, `City: Tashkent`, `Personal: Urban/Infrastructure`.
4. Сериализованная задача отправляется в **Redis** в `queue:raw_events`.

### Шаг 2: Анализ и генерация мысли (ORPHEUS + MUNINN)

1. **ORPHEUS** забирает задачу из Redis.
2. Поскольку задача содержит видео, **ORPHEUS** задействует свои медиа-модули:
* Вызывает *faster-whisper* на CPU, переводя аудиодорожку в текст.
* Направляет кадры в *Moondream2* на GPU, временно освобождая ресурсы LLM, для дешифровки визуального ряда.


3. Собрав полный текст и визуальный отчет, **ORPHEUS** обращается к **MUNINN** через HTTP REST API с запросом: *«Посмотри в ChromaDB, общались ли мы ранее в этой группе с автором поста или первыми комментаторами?»*.
4. **MUNINN** выполняет локальный семантический поиск по эмбеддингам и возвращает историю контекста.
5. Модуль `PersonaEngine` склеивает легенду бота (из статического YAML-конфига), новостные слои и память от **MUNINN**, после чего отправляет финальный промпт в текстовую модель `Qwen 2.5 3B`.
6. Сгенерированный текст проходит экспресс-тест в модуле `Guardrails` и, в случае успеха, **ORPHEUS** упаковывает готовый комментарий в Redis в `queue:execution_tasks`. Временные медиафайлы из `data_lake` полностью стираются.

### Шаг 3: Выход в сеть (MYRMIDON)

1. Свободный воркер **MYRMIDON** перехватывает задачу из Redis.
2. Сервис сверяется с базой данных PostgreSQL (`souls_accounts`), извлекая cookies сессии, логин и индивидуальный резидентный SOCKS5-прокси, жестко привязанный к этой ИИ-личности.
3. Прокси-менеджер изолирует сетевой стек эмулятора под данный IP.
4. Через встроенный Appium-драйвер скрипт открывает мобильное приложение на эмуляторе Android, находит нужную публикацию, имитирует человеческий тайминг чтения и вводит готовый текст комментария.
